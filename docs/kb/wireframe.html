Mac Stats wireframes and stack

A menu bar app for CPU, memory, network, GPU, disk I/O and disk usage. Each metric can sit in the menu bar, in the menu, or both. Click any item to see its details on top, with a short summary of every other metric below. Hover a metric in that list to open its full menu to the side.

Recommendation

Build it fully native in Swift. Use AppKit status items in the menu bar and SwiftUI inside custom panels for the dropdown and side panel. Draw big charts with Swift Charts and menu bar sparklines with Core Graphics. Keep history in memory ring buffers and save it to SQLite.

  • Ship it signed and notarized outside the Mac App Store. The App Store sandbox blocks most per-app details.
  • Two details have no public API: per-app network and per-app GPU. Treat them as experimental.

Menu bar, dropdown and side panel

This is a working wireframe with sample numbers. By default only CPU, Memory and Network are in the menu bar. GPU, Disk I/O and Disk usage are menu only: they appear at the bottom of every menu. Hover a row under Other metrics to open that metric's full menu to the side. Use the switches below to try the overview, the themes, and chart values on hover.

Menu bar display modes

Every item can use any mode. The chart in the menu bar covers a short, configurable window, such as the last 60 seconds. The dropdown chart covers the longer period you pick there.

Settings: menu bar, menu, order

Each item has two switches. Menu bar gives it a slot in the menu bar. Menu puts it in the Other metrics list and in the overview. One shared order controls all of them: drag a row, or focus it and press ⌥↑ or ⌥↓. The Menu tab picks between the item menu and the overview and has a reset to the default. Appearance is in the General tab.

    Recommended stack

    The app runs all day, so it must be light. A native Swift app can use about 1% CPU and little memory. It also reaches the low-level macOS APIs directly, with no bridge.

    LayerChoiceWhy
    LanguageSwift 6strict concurrency onCalls Mach, sysctl and IOKit directly. Actors keep sampling off the main thread safely.
    Menu bar itemsAppKit NSStatusItemone per itemItems can be added, removed and reordered at runtime. Users can also ⌘-drag them, and autosaveName keeps the order. SwiftUI MenuBarExtra is a fixed scene and handles this badly.
    Dropdown and side panelCustom NSPanel + SwiftUIborderless, non-activatingLive charts, period chips, the Other metrics list and up to three levels of hover panels need full control. A native NSMenu gives hover submenus for free. But custom views inside it are hard to update live and hard to make interactive.
    Charts in panelsSwift ChartsBuilt in and accessible. Fast enough for a few hundred points, so downsample before drawing. Hover values use chartXSelection (macOS 14) with a RuleMark as the crosshair.
    Menu bar sparklinesCore Graphics → NSImageEvery item redraws once per second. A small bitmap is much cheaper than SwiftUI or Swift Charts in the status bar.
    AppearanceNSApp.appearanceMatch system, Light, DarkSet it to nil to follow macOS, or to .aqua or .darkAqua to force a theme. SwiftUI colors and Swift Charts follow it. Menu bar sparklines are bitmaps, so redraw them when effectiveAppearance changes.
    UI stateObservation (@Observable)Views redraw only when the values they read change.
    HistoryRing buffers + SQLite via GRDB.swiftFast range reads from 1 minute to 30 days. Survives restarts. Small file on disk.
    SettingsSwiftUI Settings scene + one Codable configOne JSON document holds the item list. Each item has its order, a showInMenuBar flag, a showInMenu flag, its mode and its period. Easy to export, import and reset to default.
    Open at loginSMAppService.mainAppBuilt into macOS 13 and later. No helper app needed.
    UpdatesSparkle 2The usual update framework for apps outside the App Store.
    DistributionDeveloper ID + notarizationno App SandboxThe sandbox limits reading other processes and running tools like nettop. Per-app details need a non-sandboxed build.
    Minimum macOSmacOS 14 SonomaNeeded for Observation and a mature Swift Charts. It still covers most Macs in use.
    Project layoutApp target + local package StatsKitCollectors and the history store live in the package. You can test them without any UI.
    TestsSwift TestingTest the delta math, counter wraparound and rollups with recorded samples.
    Why not SwiftUI MenuBarExtra only?Each scene is one fixed icon. Its menu style cannot show charts. Its window style has no hover submenus.
    Why not Electron or Tauri?You still need native code for every metric. A web view also costs more memory than the whole native app.
    Why not NSMenu for the dropdown?It is a fair fallback for a first version. Plan to move to panels once charts and chips are needed.

    Where each number comes from

    Totals come from public macOS APIs. Some side-panel details do not. The tags show which is which.

    MetricTotals (menu bar and dropdown)Side panel detailsNotes
    CPU

    host_processor_info with PROCESSOR_CPU_LOAD_INFO gives user, system and idle ticks per core. Diff two samples.

    Load average: getloadavg.

    public

    Per core: the same call. P-core and E-core groups: sysctl hw.perflevel0.logicalcpu and hw.perflevel1.logicalcpu.

    Per app: proc_listallpids + proc_pid_rusage, CPU time delta.

    public    		 Root-owned processes refuse proc_pid_rusage. Read them from ps output, or show one "System" line. Temperature and clock need private SMC or IOReport access.
    Memory

    host_statistics64 with HOST_VM_INFO64 gives wired, active, inactive and compressed pages. Total: sysctl hw.memsize.

    Pressure: kern.memorystatus_vm_pressure_level. Swap: vm.swapusage.

    public

    Per app: proc_pid_rusage → ri_phys_footprint. This is the same "Memory" number Activity Monitor shows.

    public    		 Activity Monitor's exact "App memory" formula is not documented. Match it closely and explain it in a tooltip.
    Network

    sysctl NET_RT_IFLIST2 gives 64-bit byte counters per interface. Avoid the 32-bit getifaddrs counters, which wrap at 4 GB.

    public

    Per interface: the same data, plus addresses from getifaddrs.

    Per app: no public API. Take two nettop -P -L 1 samples and diff them, only while the panel is open.

    tool output    		 nettop output can change between macOS versions. The Wi-Fi network name needs Location permission. A public IP needs an outside service, so keep it off by default.
    GPU

    IOKit IOAccelerator → PerformanceStatistics: "Device Utilization %", "Renderer Utilization %", "Tiler Utilization %", memory in use.

    IORegistry

    Per app on Apple silicon: the accelerator's user-client entries carry the client pid and accumulated GPU time.

    undocumented    		 Keys differ between Apple silicon and Intel/AMD. Hide per-app GPU when the keys are missing.
    Disk I/O

    IOKit IOBlockStorageDriver → Statistics: bytes, operations and total time for reads and writes.

    public

    Per disk: one driver per physical disk. Get names through DiskArbitration.

    Per app: proc_pid_rusage → ri_diskio_bytesread and ri_diskio_byteswritten.

    public    		 Same root-process limit as CPU. One APFS disk can hold many volumes, so show disks and volumes separately.
    Disk usage

    URLResourceValues: volumeTotalCapacity and volumeAvailableCapacityForImportantUsage. The second counts purgeable space as free, like Finder.

    public

    Per volume: FileManager.mountedVolumeURLs.

    Largest folders: a background scan, only on request, with a cancel button.

    public    		 Sample every 10 minutes; it changes slowly. Scanning other apps' data needs Full Disk Access.

    How the parts fit

    Data moves one way: collectors read raw counters, the sampler runs them on a schedule, and the history store keeps the results. The UI only reads from the store. Menu-only metrics are still sampled, so their history is ready when you open a menu.

    StatsKit

    Collectors

    One per metric: CPU, memory, network, GPU, disk I/O, disk usage. Each reads raw counters and returns a typed sample. No UI code.

    actor

    Sampler

    One 1-second timer for cheap totals. Per-app scans run every 2 to 5 seconds, only while a panel is open. Slower on battery.

    StatsKit

    History store

    Ring buffers in memory plus rollup tiers. Each bucket keeps min, average and max, so short spikes survive. Saved to SQLite every 30 seconds.

    Risks and open questions

    • High

      Per-app network and per-app GPU have no public API. A macOS update can break either one. Put both behind feature flags and hide them when they fail.

    • High

      No Mac App Store. The sandbox blocks most per-app details. Plan Developer ID signing, notarization and Sparkle from day one.

    • Medium

      Root-owned processes hide their numbers. Decide early: read them from ps, or show them as one "System" line.

    • Medium

      Menu bar space. On MacBooks with a notch, macOS hides items that do not fit. Menu-only items and the compact group mode both help.

    • Medium

      Tall menus. Details plus six summary rows is about 650 points tall. On a small screen, cap the chart height and let the Other metrics list scroll.

    • Medium

      Energy use. A 1-second timer is fine when collectors are cheap. Measure with Instruments early. Pause drawing when the screen is locked or the display sleeps.

    • Question

      Separate order for the menu? This draft uses one shared order for the menu bar and the menu. A second order is possible but makes settings harder to read.

    • Question

      Temperature, fans and power? They need private SMC or IOReport access. They are left out of version 1 unless you want them.

    • Question

      Intel Macs? Supporting them adds test work, and the GPU keys differ. Apple silicon only is simpler.
